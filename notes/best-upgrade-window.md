# 最佳升级时间窗：环形滑动窗口复盘

## 原来的思路

使用双指针维护滑动窗口。为了支持跨周期窗口，把长度为 `n` 的数组看成长度约为 `2n` 的虚拟数组，通过 `% n` 访问原数组。

这个总体方向是正确的，目标时间复杂度为 `O(n)`，额外空间复杂度为 `O(1)`。

## 出现的错误

### 1. 只维护了累计访问量，没有维护最大窗口长度

最初只在下面的条件成立时收缩窗口：

```text
sum > cap
```

但题目要求合法窗口同时满足：

```text
sum <= cap
windowLength <= n
```

结果是当 `cap` 足够大时，程序可能接受超过一个周期的窗口。例如所有元素都是 `1`、`cap = 200` 时，错误实现会得到长度为 `200` 的窗口，但合法长度最多为 `168`。

### 2. 更新答案前没有验证候选窗口是否合法

最初更新答案时只比较：

```text
windowLength > maxLength
```

如果收缩因为起点到达周期末尾而停止，此时 `sum` 仍可能大于 `cap`。没有再次验证合法性，就可能把非法窗口写入答案。

例如数组全为正数且 `cap = 0` 时，本应返回 `[-1, -1]`，错误实现却可能记录起点为 `168` 的窗口。

### 3. 虚拟下标和真实数组下标的模型不够明确

`right` 使用虚拟下标，并通过下面的方式访问真实数组：

```c
visitCnt[right % n]
```

而 `left` 被限制在第一周期，所以曾直接使用 `visitCnt[left]`。这种写法在限制成立时可以工作，但代码本身不容易让人立即确认这个不变量。

以后应明确选择一种模型：

- 左右指针都使用虚拟下标，访问数组时统一 `% n`；
- 或者明确规定起点只在第一周期，并在代码中保证 `left < n`。

### 4. 循环上界靠直觉书写，没有从合法窗口推导

最大起点是 `n - 1`，最大窗口长度是 `n`，所以最大虚拟结束下标是：

```text
(n - 1) + (n - 1) = 2n - 2
```

因此扫描范围可以写成：

```text
right < 2n - 1
```

直接写 `right < 2n` 会额外扫描一个重复位置。即使最终结果未必出错，也会让边界更难证明。

### 5. 混用 `int` 和 `size_t`

原实现中：

- `left`、`right`、`maxLength` 使用 `int`；
- `visitCntSize` 和 `sum` 使用 `size_t`。

这会产生有符号与无符号比较、隐式类型转换等编译器警告，也增加边界判断出错的概率。

累计访问量还可能远大于单个 `int`，因此更适合使用 `uint64_t`。

## 错误的根本原因

### 1. 写代码前没有列出完整的合法窗口条件

只关注了题目中最显眼的 `sum <= cap`，遗漏了长度、起点范围和环形映射。

### 2. 没有先确定循环不变量

没有明确“收缩结束后窗口必须满足什么”，导致更新答案时需要临时补充判断，也容易漏掉条件。

### 3. 没有从数学范围推导循环边界

虚拟数组的结束位置凭经验写成 `2n`，而不是根据最大起点和最大长度计算。

### 4. 主要依赖官方样例，没有让每条规则对应一个测试

普通样例不一定能暴露超过最大长度、完全无解、整数溢出等问题。

### 5. 没有及时处理编译器警告

类型警告经常意味着比较双方的取值范围和语义没有设计清楚。即使当前数据规模不会触发错误，也不应直接忽略。

## 更稳妥的解题流程

### 写代码前

先写出本题合法窗口的定义：

```text
0 <= start < n
1 <= windowLength <= n
sum <= cap
end = virtualRight % n
```

然后确定变量含义：

```text
left、right：虚拟数组下标
sum：当前窗口的累计访问量
maxLength：当前最佳窗口长度
```

### 写循环时

按照固定顺序处理：

```text
1. 加入 right 对应的元素
2. 当访问量超限或长度超限时移动 left
3. 确认窗口合法
4. 使用严格大于更新最长窗口
5. 将虚拟结束下标映射回原数组
```

严格使用 `windowLength > maxLength`，而不是 `>=`，这样遍历顺序中更早出现、开始下标更小的答案会被保留。

### 类型选择

```text
数组下标和长度：size_t
累计访问量：uint64_t
返回结构中的下标：int
```

只有在确认题目保证下标可以由 `int` 表示后，才在写入返回结果时进行显式转换。

## 下次检查清单

### 滑动窗口

- [ ] 窗口采用 `[left, right]` 还是 `[left, right)`？
- [ ] 窗口合法需要满足哪些条件？
- [ ] 收缩循环结束后是否一定合法？
- [ ] 左右指针每轮是否保证前进？
- [ ] 更新答案是在收缩前还是收缩后？
- [ ] 并列答案应该保留旧答案还是覆盖？

### 环形数组

- [ ] 哪些变量是虚拟下标？
- [ ] 每次真实数组访问是否正确使用 `% n`？
- [ ] 起点是否被限制在第一个周期？
- [ ] 最大虚拟结束下标是否由公式推导？
- [ ] 窗口长度是否被限制为最多 `n`？

### C 语言

- [ ] 下标和数组长度是否使用兼容类型？
- [ ] 累计和是否可能超过 `int`？
- [ ] 是否存在有符号与无符号比较警告？
- [ ] 取模前是否保证除数不为 `0`？
- [ ] 写入较窄类型前是否确认范围安全？

## 针对性测试

| 场景 | 目的 |
| --- | --- |
| 官方三个样例 | 检查基本规则和跨周期窗口 |
| 全为 `1`，`cap = 0` | 检查无解是否返回 `[-1, -1]` |
| 全为 `0`，`cap = 0` | 检查能否选择完整周期 |
| 全为 `1`，`cap = 2` | 检查并列时选择最小起点 |
| 元素全为 `INT_MAX` | 检查累计值是否溢出 |
| 最优窗口从下标 `167` 开始 | 检查跨周期和最大虚拟下标 |

## 本题应记住

1. 滑动窗口维护的不是单独一个 `sum`，而是满足题目全部约束的合法区间。
2. 环形数组要区分虚拟下标与真实下标，窗口长度必须额外限制为不超过一个周期。
3. 边界应该通过最大合法状态推导，不要凭感觉多循环一次。
4. 编译器警告和针对性边界测试都是解题过程的一部分。
