# 收银台设计：有限库存找零复盘

## 原来的思路

使用长度为 `5` 的数组记录 `1、5、10、50、100` 元钞票的数量。处理每笔付款时，先把收到的钞票加入临时库存，再从大面额向小面额贪心找零；找零成功才更新收银台，失败则保留原状态。

这个总体方向是正确的。由于面额 `{1, 5, 10, 50, 100}` 具有整除关系，在库存限制下优先使用尽可能多的大面额，可以得到最少钞票数量。目标时间复杂度为 `O(paymentsSize)`，额外空间复杂度为 `O(1)`。

## 出现的错误

### 1. 把商品价格当成找零金额

早期实现直接分解：

```c
int p = payments[i].price;
```

然后从收银台中减去组成 `price` 的钞票。实际上应该计算：

```text
change = paidTotal - price
```

并从“原库存加本次付款”中扣除组成 `change` 的钞票。

每笔成功交易应保持以下金额不变量：

```text
交易后总金额 = 交易前总金额 + price
```

### 2. 把钞票张数当成付款金额

错误实现曾写成：

```c
sum += payments[i].paidCashes[j];
```

这只能得到总张数。例如一张 `1` 元和一张 `5` 元会得到 `2`，而不是付款金额 `6`。

金额必须由“张数乘面额”得到：

```text
paidTotal += paidCashes[j] * units[j]
```

这是一次“单位”混淆：`paidCashes[j]` 的单位是张，`price` 的单位是元，两者不能直接比较。

### 3. 先按无限库存分解，再检查钞票够不够

早期实现先用无限库存贪心计算每个面额需要多少张，然后只要某个大面额不足就判定失败。这会漏掉使用更多小面额的可行方案。

例如：

```text
初始库存：[0,2,0,0]
价格：40
付款：[0,0,0,1,0]
```

需要找零 `10` 元。没有 `10` 元钞票，但可以使用两张 `5` 元。正确做法是在每个面额上使用：

```text
used = min(change / denomination, availableCount)
```

然后继续尝试更小面额。

### 4. 更新剩余找零金额时乘错变量

错误实现曾写成：

```c
temp[k] -= num;
price -= num * temp[k];
```

`temp[k]` 是扣除后的剩余钞票张数，不是钞票面额。使用 `num` 张当前面额钞票后，应减少的金额是：

```text
num * units[k]
```

这也是张数和金额再次混淆。

### 5. 没有以“剩余找零金额为零”判定成功

仅仅没有出现负库存，不代表已经凑出全部找零。贪心循环结束后必须检查：

```text
change == 0
```

只有该条件成立，才能把临时库存提交到正式库存。

### 6. 动态内存分配的字节数错误

错误实现写成：

```c
int *res = malloc(5);
```

这只分配 `5` 字节，不是 `5` 个 `int`。随后写入 `res[1]` 到 `res[4]` 会造成堆越界和未定义行为。

正确的大小表达方式是：

```c
int *res = malloc(5 * sizeof *res);
```

使用 `sizeof *res` 可以避免类型改变后忘记同步修改。

### 7. `memset` 的长度和调用顺序错误

错误实现写成：

```c
memset(res, 0, 5);
```

第三个参数也是字节数，所以这同样只清零 `5` 字节。应使用 `5 * sizeof *res`，并且必须在确认 `res != NULL` 后调用。

本题实际上会显式写入前四项，因此也可以只写：

```c
res[4] = 0;
```

从而不需要 `memset`。

### 8. 依赖测试文件间接提供头文件

`solution.c` 使用了：

- `bool`、`true`、`false`，需要 `<stdbool.h>`；
- `memset`，需要 `<string.h>`。

本地 `test.c` 先包含 `test.h`，可能间接提供这些声明，使联合编译看似正常；但单独提交或编译 `solution.c` 时会失败。答案文件必须直接包含自己使用的标准头文件。

### 9. 丢弃了 `const` 限定

参数 `payments` 是只读的，因此：

```c
int *paidCashes = payments[i].paidCashes;
```

会丢弃 `const` 并产生编译器警告。只读别名应写成：

```c
const int *paidCashes = payments[i].paidCashes;
```

## 错误的根本原因

### 1. 没有先写清变量的单位和含义

代码中先后混淆了：

- 钞票张数与金额；
- 商品价格与找零金额；
- 剩余钞票张数与当前面额。

以后在写循环前，应先为每个变量标注语义：

```text
paidCashes[j]：张数
units[j]：元/张
paidTotal、price、change：元
res[j]、available[j]、used：张数
```

### 2. 没有先确定交易状态不变量

收银失败必须完全回滚，不能让本次收到或尝试找出的钞票影响下一笔交易。因此不能直接修改 `res`，而应在临时库存中试算，成功后再提交。

### 3. 把数学上的无限硬币贪心直接套到有限库存

库存是题目的核心约束。每次选择钞票数量时，都必须同时考虑剩余找零金额和当前库存。

### 4. 对 C 内存函数的参数单位不敏感

`malloc` 和 `memset` 接收的是字节数，不是元素数量。只写常数 `5` 容易忽略 `int` 通常占多个字节。

### 5. 测试文件的包含顺序掩盖了答案文件问题

联合测试能编译不代表 `solution.c` 能独立提交。编译检查需要同时覆盖：

```text
单独检查 solution.c
通过 test.c 检查完整测试程序
```

## 更稳妥的处理流程

每笔付款按照固定顺序处理：

```text
1. paidTotal = Σ(paidCashes[j] * units[j])
2. 如果 paidTotal < price，交易失败
3. available[j] = res[j] + paidCashes[j]
4. change = paidTotal - price
5. 从 100 元到 1 元进行有限库存贪心
6. 如果 change != 0，交易失败并丢弃 available
7. 如果 change == 0，把 available 复制到 res
```

有限库存贪心的循环不变量是：

```text
进入某个面额前，change 表示尚未找出的金额；
available[j] 表示该面额当前最多可以使用的张数；
处理后不会使用超过库存的钞票。
```

- [ ] 大面额不足时是否继续尝试小面额？

- [ ] 付款不足时是否保持库存不变？

## 针对性测试

| 场景 | 输入要点 | 预期检查 |
| --- | --- | --- |
| 官方样例 | 连续三笔交易 | 收款、失败回滚和本次钞票参与找零 |
| 精确付款 | 价格 `6`，付款一张 `1` 元和一张 `5` 元 | 收到的两张钞票全部入账 |
| 付款不足 | 价格 `10`，付款一张 `5` 元 | 库存完全不变 |
| 无法找零 | 无零钱，价格 `1`，付款一张 `5` 元 | 交易失败并退回付款 |
| 优先大面额 | 同时有一张 `10` 元和两张 `5` 元 | 找零 `10` 元时使用一张 `10` 元 |
| 大面额不足 | 只有两张 `5` 元 | 找零 `10` 元时使用两张 `5` 元 |
| 失败后继续交易 | 第一笔找零失败，第二笔精确付款 | 第一笔不能污染第二笔状态 |

## 本题应记住

1. 先写出金额不变量：成功交易后，收银台总金额只增加商品价格。
2. 张数、面额和金额是三个不同量，任何加减乘都要检查单位是否一致。
3. 有限库存贪心必须把每次使用量限制在现有库存内，并以剩余金额为零判定成功。
4. 可能失败的状态更新应先在副本上试算，成功后再提交。
5. `malloc` 和 `memset` 的大小参数都是字节数，答案文件还必须能独立编译。
